# Вкладка «Аналитика» в админке — план и спецификация

Составлено 15.08.2026 (этап 1, проектирование). Документ — рабочее задание для
следующих этапов; их можно вести в новых сессиях и другими моделями, поэтому
здесь всё, что нужно знать, без отсылок к переписке.

## 1. Что делаем и для кого

Вкладка админки **«Аналитика»**, видна **только владельцу** (аккаунт
`dima24ba@gmail.com`; список — одна константа, добавить второй адрес — одна
строка). Внутри — графики по двум источникам, обновляемые автоматически:

1. **Wordstat по регионам** — поисковый спрос на отопление, материалы, бренды.
2. **Догазификация** — планы подключения посёлков к газу по регионам.

Позже сюда же добавятся другие блоки (свои сметы как опережающий индикатор,
ипотека ИЖС, погода, тендеры и т.д.) — вкладка проектируется как набор
независимых блоков, каждый со своим JSON и своим парсером.

**Главное ограничение, заданное владельцем:** считаем только регионы, где
калькулятор реально присутствует — есть монтажники, дистрибьюторы или объекты
смет. Регионы без пользователей не анализируем и не показываем.

## 2. Архитектурные решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где крутятся парсеры | Python + GitHub Actions, как `AutoTariff.py` / `update-tariffs.yml` | уже отлаженный путь, ключи в GitHub Secrets |
| Куда пишем результат | файлы `analytics/wordstat.json`, `analytics/wordstat_pulse.json`, `analytics/gas.json` в репозитории (коммит ботом) | статика раздаётся с GitHub Pages бесплатно; Supabase не трогаем — лимит egress 5 ГБ/мес уже упирались |
| Как вкладка получает данные | `fetch('analytics/….json?ts=<месяц>')` при открытии вкладки, лениво | обычные пользователи файлы не качают вообще |
| Графики | Chart.js, вендорим в `vendor/chart.umd.js`, грузим `<script>` только при открытии вкладки | тултипы/легенды из коробки, ~200 КБ никого кроме админа не касаются |
| Расписание Wordstat | полный снимок **3-го числа каждого месяца** (Яндекс закрывает прошлый месяц в первые дни) + короткий «пульс» **по понедельникам** | месячная история — для трендов, недельный пульс — чтобы видеть начало сезона не с месячным опозданием |
| Расписание догазификации | **15-го числа ежемесячно** | планы меняются редко |
| Список «живых» регионов | RPC-функция Supabase `analytics_live_regions()` (только названия, без счётчиков), вызывается парсером с публичным anon-ключом | парсеру нужен актуальный список каждый запуск; названия регионов без цифр — не секрет, а служебный ключ в Actions отдавать не хотим |
| Канонические имена регионов | как в `cities_geo.js` → `CITY_GEO[город].region` и ключах `el_tariffs.js` (короткие формы республик: «Бурятия», «Чувашия», «Алтай») | к этим ключам уже привязаны тарифы и города; всё сводим к ним |

### 2.1. «Живые» регионы — откуда

Объединение трёх источников (distinct, без счётчиков):

- `public.users.region` — при регистрации приводится к списку `VALID_REGIONS`
  (app.js, поиск по `const VALID_REGIONS`), там **длинные** формы:
  «Республика Бурятия», «Кабардино-Балкарская Республика».
- `public.distributors.regions` — массив `text[]`, свободный ввод через запятую
  (`dist_regions`), нормализуется тем же кодом.
- `public.shared_invoices.object_info->>'region'` — это **название города**,
  если в смете выбран город (`state.selectedCity.name`), иначе климатическая зона
  («Центр», «Сибирь», «Урал», «Юг») — зоны отбрасываем, города переводим в
  регион через `CITY_GEO` (cities_geo.js) и словарь город→регион в catalog.js
  (поиск по `"калининград": "Калининградская область"`).

Приведение к каноническим именам делает парсер (Python), а не SQL: у него под
рукой `cities_geo.js` (регуляркой вытащить `"Город": {…region: "…"}` — как
AutoTariff читает свои файлы). Таблица соответствий длинных форм коротким —
явная, в коде парсера (`"Республика Бурятия" → "Бурятия"` и т.п.); незнакомое
имя — в лог, не молча.

**Стоп-список.** Отбрасывать климатические зоны калькулятора («Центр», «Юг»,
«Урал», «Сибирь» — это не регионы, а значения `state.region`) и федеральные
округа («УРФо», «ЦФО», «федеральный округ» в названии). Регистрация в app.js
округа уже не принимает (проверка `fedDistricts`), но в базе такие записи
остались, и в поле регионов дистрибьютора ввод свободный.

**Фактический состав на 15.08.2026** (функция выполнена, 18 строк): 10 живых
субъектов — Архангельская, Калининградская, Костромская, Ленинградская,
Московская, Мурманская, Свердловская области, Республика Карелия, Москва,
Санкт-Петербург. Плюс отброшенные «Урал», «Центр», «УРФо». Из городов смет:
Калининград и Санкт-Петербург — оба сводятся к уже имеющимся субъектам.

Черновик миграции (короткий — редактор Supabase обрезает длинные вставки,
см. память проекта):

```sql
-- supabase/migrations/20260815_analytics_live_regions.sql
-- Список регионов присутствия для парсеров аналитики (GitHub Actions).
-- Только названия, без счётчиков: вызывается anon-ключом.
create or replace function public.analytics_live_regions()
returns table(kind text, name text)
language sql security definer set search_path = public as $$
  select 'user', region from public.users where region is not null and region <> ''
  union
  select 'dist', unnest(regions) from public.distributors where regions is not null
  union
  select 'city', object_info->>'region' from public.shared_invoices
   where object_info->>'region' is not null;
$$;
revoke all on function public.analytics_live_regions() from public;
grant execute on function public.analytics_live_regions() to anon, authenticated;
```

Вызов из парсера: `POST https://<project>.supabase.co/rest/v1/rpc/analytics_live_regions`
с заголовками `apikey` и `Authorization: Bearer <anon-ключ>` (anon-ключ —
`supabaseKey` в начале app.js, он публичный). Если RPC недоступен — парсер
берёт список из прошлого `analytics/*.json` и пишет предупреждение, а не падает.

Счётчики (сколько смет в каком регионе — для приоритета адаптеров догазификации
и для сортировки во вкладке) публично не отдаём: во вкладке их считает сам
админ своими правами, для этапа 3 — запрос в SQL-редакторе Supabase владельцем.

Написаны `AutoWordstat.py`, `analytics/wordstat_phrases.json`,

его тут нет и не должно быть): синтаксис; нормализация всех 137 форм

и живых 18 строк `analytics_live_regions()`; математика дат (границы
месяцев, високосный год, недели); сопоставление с деревом регионов на
подложном ответе Yandex; возобновление backfill после обрыва (обрыв на
середине → повторный запуск обрабатывает только недостающие пары, не всё
заново); полный цикл `run_monthly`/`run_backfill`/`run_pulse` на поддельном
клиенте — числа запросов совпали с бюджетом плана (53 в стационарном
режиме, 21 у backfill на 2 регионах, 10 у pulse).

Два бага нашлись и исправлены именно на этих прогонах, не при чтении кода:
(1) `clear_state()` вызывался из докатки нового региона внутри `run_monthly`
и мог стереть прогресс ещё не завершённого ручного `--backfill` — теперь
файл состояния чистит только сам `--backfill`, когда закрыт его полный
список пар; (2) холодный старт (пустой `wordstat.json`) распознавался как
«все регионы новые» и тихо запускал внутри обычного `monthly` эквивалент
полного backfill (сотня запросов, полтора часа) — теперь `monthly` на
пустой истории только предупреждает и просит запустить `--backfill`
отдельно, докатка остаётся только для регионов, появившихся ПОСЛЕ того,
как история уже у кого-то есть.

Не проверено (нечем — ключ только в GitHub Secrets): реальный формат
ответов Yandex Search API, реальные `yid` регионов, поведение на живой
квоте. Первый прогон в Actions — обязательно `--pulse` (10 запросов,
≈0,2 ₽), потом `--backfill` (~100 запросов, час-полтора), и только потом
можно доверять расписанию `monthly`/`pulse`.

### 3.1. Доступ к API

Два варианта, скрипт поддерживает оба через переменные окружения (GitHub Secrets):

**Доступ настроен 15.08.2026** (владелец): облако `cloud-kovdor24`, каталог
`default` `b1galb7ln8r9vtillbnv`, сервисный аккаунт `wordstat-parser` с ролью
`search-api.webSearch.user`, API-ключ с областью действия
`yc.search-api.execute` (бессрочный). Секреты репозитория `terem24/smeta`:
`WORDSTAT_API_KEY`, `WORDSTAT_FOLDER_ID`.

Запрос: `POST`, заголовок `Authorization: Api-key <ключ>` (в документации
именно так, со строчной `k`), тело — JSON, `folderId` обязателен **в теле**
каждого запроса. Все числовые поля ответа приходят **строками** (int64 в
protobuf) — разбирать в int.

Методы (сверено по документации 15.08.2026):

| Метод | Адрес (`https://searchapi.api.cloud.yandex.net`) | Что даёт | Цена за 1000 запросов |
|---|---|---|---|
| GetDynamics | `POST /v2/wordstat/dynamics` | частота фразы по периодам; `period` = `PERIOD_MONTHLY` / `PERIOD_WEEKLY` / `PERIOD_DAILY`, `fromDate`/`toDate` в RFC3339 (для месяца — первый и последний день, для недели — понедельник и воскресенье), `regions[]` (до 100 id, **суммирует** их, а не разбивает), `devices[]`. Ответ: `results[].date/count/share` | 20 ₽ |
| GetRegionsDistribution | `POST /v2/wordstat/regions` | распределение фразы по регионам **за последние 30 дней**, одним запросом на всю страну. Параметр `region`: `REGION_REGIONS` (субъекты — наш случай), `REGION_CITIES`, `REGION_ALL`. Периода нет. Ответ: `results[].region/count/share/affinityIndex` | 50 ₽ |
| GetTop | `POST /v2/wordstat/topRequests` | популярные запросы с фразой за 30 дней + похожие (`associations`, максимум 20); `numPhrases` 1…2000 | 20 ₽ |
| GetRegionsTree | `POST /v2/wordstat/getRegionsTree` | дерево регионов Wordstat (`id`, `label`, `children`) | бесплатно |

Цены с НДС, тарифицируется каждый запрос; запросы, упавшие с ошибкой сервера
или авторизации, не тарифицируются. При наших объёмах (см. 3.2) выходит
**около 10 ₽ в месяц**; до 14.10.2026 действует стартовый грант 4000 ₽.

Квоты Wordstat: **10 запросов в секунду и 100 запросов в час** (не «1000 в
сутки» — это лимит старого API). Часовой потолок и есть главное ограничение,
под него подстроен бюджет запросов ниже. Квоту можно поднять запросом в
поддержку, если понадобится.

Ограничения: длина фразы до 400 символов, до 40 слов. `GetDynamics` при
детализации по неделям и месяцам поддерживает только оператор `+` (остальные —
только для дней); мы операторами не пользуемся.

Запасной путь (если основной закроют) — старый API Вордстата
`https://api.wordstat.yandex.net`: OAuth-приложение + заявка на доступ,
`Authorization: Bearer <токен>`, 1000 запросов в сутки, бесплатно.
Справка: https://yandex.ru/support2/wordstat/ru/content/api-wordstat

Документация основного пути (для робота закрыта капчей, открывать в браузере):
https://aistudio.yandex.ru/docs/ru/search-api/concepts/wordstat,
`.../api-ref/Wordstat/getDynamics`, `.../operations/wordstat-getdynamics`,
квоты `.../concepts/limits`, тарифы `.../search-api/pricing`.

Первый запуск — «дымовой» запрос одной фразы каждым методом и распечатка
сырого ответа: формат зафиксировать в комментарии скрипта, потом писать разбор.

### 3.2. Бюджет запросов и что именно собираем

Потолок 100 запросов в час диктует устройство: тяжёлый разовый сбор истории
отделён от лёгких регулярных запусков.

**Разовый backfill (`--backfill`, запускается руками один раз):**
- **Динамика по регионам** (`dynamics`, `PERIOD_MONTHLY`, с 2018-01-01,
  `regions: [id]` — по одному региону на запрос): core-фразы × живые регионы.
  По факту на 15.08.2026: 10 core × 10 регионов = 100 запросов ≈ 2 ₽,
  час-полтора с учётом часовой квоты.
  Скрипт держит темп ≤ 90 запросов в час и пишет прогресс в
  `analytics/.wordstat_state.json`; при обрыве повторный запуск продолжает
  с места остановки, а не начинает заново.
- Когда в базе появляется **новый живой регион**, следующий обычный запуск сам
  делает backfill только по нему (10 запросов) — регионы не копятся в долг.

**Ежемесячный запуск (3-го числа), ~53 запроса, укладывается в один час:**
- `regions` (`REGION_REGIONS`) — 1 запрос на фразу, все 24 фразы: приходит вся
  страна, храним только живые регионы. **История по регионам копится из этих
  снимков** — потому и не нужно каждый месяц дёргать динамику по регионам.
- `dynamics` `PERIOD_MONTHLY` по России с 2018 — 1 запрос на фразу, 24 фразы
  (переписываем ряд целиком: дешевле, чем сшивать хвосты).
- `topRequests` — 5 «широких» фраз, по России; храним последний снимок и
  предыдущий, чтобы показывать дельту.

**Недельный пульс (понедельник, `--pulse`), 10 запросов:** `dynamics`
`PERIOD_WEEKLY` за последние 12 недель для core-фраз по России. По регионам
пульс не гоняем — на недельном шаге региональные числа шумные, а квота дорога.

Пауза между запросами: не чаще 10 в секунду **и** не больше 90 в час
(скользящее окно). При 429/503 — экспоненциальная пауза, до 3 повторов.
Запуск считается неудачным (exit 1, файлы не перезаписываем), если получено
меньше 80 % запланированных ответов.

```json
  "top_requests": {"2026-08": {"montazh_otopleniya": [["монтаж отопления в частном доме цена", 3456]]}}
}
```

Ориентир по размеру: 25 фраз × 20 регионов × ~100 месяцев ≈ 400 КБ. Если
вырастет за 1 МБ — `region_monthly` резать до последних 5 лет.

`analytics/wordstat_pulse.json`: `{"updated", "weeks": ["2026-W30", …],
"ru": {phraseId: [числа]}}` (по регионам пульс не собираем, см. 3.2).

### 3.6. Workflow `.github/workflows/update-wordstat.yml`

По образцу `update-tariffs.yml`: `schedule` — `'0 5 3 * *'` (полный) и
`'0 5 * * 1'` (пульс, запуск с `--pulse`); `workflow_dispatch` с выбором режима
(`monthly` / `pulse` / `backfill`) — backfill только руками; секреты через
`env` (`WORDSTAT_API_KEY`, `WORDSTAT_FOLDER_ID`); `timeout-minutes: 300` —
backfill идёт часами из-за часовой квоты; коммит только если файлы изменились;
ретрай `git pull --rebase && git push`. Зависимости — стандартная библиотека
Python.

Проверять парсер локально нечем (ключ лежит только в секретах GitHub) —
первый прогон делать через вкладку Actions → Run workflow, режим `pulse`
(10 запросов, ~0,2 ₽), и смотреть лог.

## 4. Этап 3 — догазификация (`AutoGasPlans.py` + адаптеры)

**Модель:** Opus 5 (или Fable 5), высокий уровень: источники разнородные,
придётся разбираться по месту.

### 4.1. Что выяснено про источники (15.08.2026)

- Единого машиночитаемого источника **нет**.
- gazprommap.ru: страницы регионов (`https://gazprommap.ru/<slug>/`) содержат
  только список ГРО и статьи — показателей и планов там нет.
- connectgas.ru (Единый оператор газификации): «Проверить адрес»
  (`/gasification_program`) и интерактивные карты по регионам; открытых
  выгрузок/API не видно. Первое, что сделать на этапе 3 — открыть страницу
  проверки адреса в браузере с инструментами разработчика и посмотреть, каким
  запросом она ищет населённый пункт: если это простой JSON-эндпоинт, он может
  стать **универсальным** источником для посёлков в радиусе ~50 км от живых
  городов (`CITY_GEO`), без адаптеров на регион.
- План-графики по посёлкам живут у регионов, форматы разные: Мособлгаз
  (https://mosoblgaz.ru/gazification/), комитет ТЭК Ленобласти
  (https://tek.lenobl.ru/… «Программы газификации», таблицы), геопортал
  Калужской области (интерактивная карта), у остальных — PDF/HTML на сайтах
  правительств и ГРО.

**Особый случай — Мурманская область и Карелия (уточнено владельцем
15.08.2026).** Мурманская область исторически без сетевого газа (мазут, уголь,
электричество), но в 2025 году «Газпром» начал строить магистраль
**Волхов — Мурманск**, более 1300 км, срок — 2030 год; трасса идёт из
Ленинградской области **через Карелию** на Кандалакшу, Апатиты, Мурманск.
Действует первая программа газификации области **2026–2030**; первый этап —
перевод на газ 24 крупных объекта теплоснабжения (в том числе Апатитская и
Мурманская ТЭЦ), то есть частные дома пойдут позже, после распределительных
сетей.

Что это значит для вкладки: у Мурманской области показывать не «нет данных», а
**таймлайн стройки магистрали и программы 2026–2030** (этап, год, что именно
переводится). Регион не выпадает из аналитики, а становится примером
опережающего сигнала: рынок газового оборудования там появится целиком, и
монтажник видит срок заранее. Карелия — тот же сюжет, но она попадает под
трассу раньше. Пока газа нет, для Мурманской области практичнее показывать
электрическую ветку (тариф из `el_tariffs.js`, спрос на электрокотлы и
тепловые насосы из Wordstat) — там сейчас реальный спрос.
Источники: gazprom.ru (пресс-релиз 10.2025), interfax.ru, portnews.ru.

### 4.2. Устройство

- `analytics/gas_adapters/<region_slug>.py` — по адаптеру на регион; общий
  интерфейс: `fetch() -> {"source": url, "fetched": дата, "settlements":
  [{"name", "district", "year", "households" (если есть), "status"}]}`.
- `AutoGasPlans.py` — гоняет адаптеры **только для живых регионов**
  (список — тот же RPC), собирает `analytics/gas.json`:
  `{"updated", "regions": {region: {"source", "fetched", "settlements": […],
  "by_year": {"2026": {"settlements": n, "households": m}}, "note"}}}`.
  Регионы живые, но без адаптера — попадают в `gas.json` с `"note":
  "нет источника"` — вкладка покажет их списком «нужен адаптер».
- Расстояние посёлка до живых городов считает вкладка (координаты городов —
  `CITY_GEO`; координаты посёлков — если адаптер их отдал; иначе — по району).
- Один упавший адаптер не роняет запуск: регион получает `note` с ошибкой,
  предыдущие данные региона сохраняются из старого `gas.json`.
- Workflow `update-gas-plans.yml`: `'0 5 15 * *'` + `workflow_dispatch`.

### 4.3. Порядок

1. Владелец даёт счётчики смет/монтажников по регионам (SQL-редактор Supabase,
   запрос ниже) — по ним приоритет адаптеров.
2. Проверка connectgas на универсальный эндпоинт (см. 4.1).
3. Первые адаптеры — из десяти живых регионов (список в 2.1): Московская,
   Ленинградская, Калининградская области; затем Свердловская, Архангельская,
   Костромская. Мурманская и Карелия — не адаптер к плану-графику по посёлкам,
   а таймлайн магистрали и программы 2026–2030 (см. выше), это отдельный,
   более простой сборщик.

```sql
-- Приватный запрос владельца: сметы по регионам (города → регион переводит
```
